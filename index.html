Abstract

Question → Method → Result

Which pages should a content team review first when they only have time to check a handful each week? I built a ranked scoring system on FlyRank's anonymized search-performance data to answer this. A transparent CTR-gap baseline rule was defined first, then compared against a Random Forest classifier trained under a client-grouped holdout — the same clients never appear in both train and test. Measured honestly, the model reaches a Precision@50 of 0.74 against the baseline's 0.66; a naive random split on the same data inflates this to a misleading 0.94, which is itself the paper's central methodological finding. The output is not a prediction of the future — it is a ranked review queue with reason codes, explicit limits, and a no-go list for what should never be automated.

01

Introduction

Every content team has more pages than time. A reviewer with capacity for fifty pages a week needs to know which fifty matter — not a dashboard of every metric, and not a black-box score they cannot question.

FlyRank's own product already computes rule-based flags (staleness, CTR issues, quick wins) to help with this. This project asks a narrower, testable question: on the same kind of signal a rule already uses, can a learned model rank candidates more accurately than a single hand-written formula — and if so, by how much, measured honestly?

The unit of analysis throughout is a single content page, for a single client, aggregated over a trailing window. The decision it supports is: which pages does a reviewer open first this week.

What was deliberately excluded

FlyRank's own product decision fields — health_score, priority_score, action_type — are not present in this data and were never reconstructed as features or labels. Using a product's own decision as a training input would only teach a model to copy that decision, not discover independent signal. Raw client names, domains, URLs, and private queries never appear in this data, this paper, or the repository.

03

Methodology

Label

The target is a proxy, stated plainly: is_declining = trend_direction == "down", a bucket computed within the same window as the features. This is a current-window signal, not a confirmed future outcome — the single most important limitation of this work, discussed further below.

Features

Seven observed signals, all knowable at the decision moment: impressions_90d, sessions_90d, avg_position, ctr, content_age_days, engagement_rate, word_count. None are derived from the label, and none require information from after the decision point.

Baseline

A transparent rule was built first, so the model has something honest to beat: score = (expected_ctr_for_position_tier − actual_ctr) × log(1 + impressions_90d). Expected CTR by position tier was measured directly from the data (33.7% at position 1–3, falling to 13.1% at position 20+), confirming CTR-vs-position as a real, usable signal. A parallel check on content age found the opposite of the common assumption — older content declined less often (42.7%) than newer content (68.1%) in this slice — so raw content age was deliberately excluded from the baseline rule.

Validation design

Pages from the same client can share site-wide patterns a model could memorize rather than generalize from. All results below use a client-grouped holdout (25% of clients held out entirely) so no client's pages appear in both train and test. This single design choice is the paper's core methodological argument, demonstrated directly in the Results section.

Leakage audit

Every feature was checked against five questions before use: is it computed after the decision point, does the feature window overlap the target window, does it reconstruct a product flag, does it secretly encode the label, and are related rows split unfairly across train/test. All five checks passed on the final feature set.

Error analysis

On the honest test set, the model produced 933 false negatives (a real decline ranked too low to be reviewed) against 906 false positives (a stable page flagged unnecessarily). For this lane, a missed decline is the more costly error — it means a real problem goes unreviewed until the next cycle — so a production threshold would lean toward catching more true declines at the cost of a few extra false positives.

05

Limitations & honest framing

The label is a proxy, not a future outcome trend_direction == "down" is a bucket computed in the same window as the features. This model measures "does this page resemble others already tagged as declining," not "will this page decline next month." A stronger future version would build a true prior-90-days → next-30-days label from the warehouse's daily facts.
  • All reported numbers come from a 30,000-row anonymized starter slice, not the full ~79 million-row warehouse — directional evidence, not a production benchmark.
  • Precision@50 of 0.74 is a sample average; it is not a guarantee for any single page or client.
  • No causal claim is supported by this data. A high score means "worth reviewing," never "refreshing this page will fix it" — that would require a controlled experiment this dataset cannot provide.
  • No FlyRank product decision flag (health_score, priority_score, action_type) was used, reconstructed, or approximated anywhere in this work.

What must never be automated

  • No page is auto-published or auto-edited from this score — the output is a review queue, not an editing pipeline.
  • The score is never used to make client-facing promises about recovered traffic.
  • A "protect_monitor_only" tag is not deprioritized without a human check, since a missed decline is costlier than a wasted review.
  • "Monitor" does not mean "no traffic" — it means the page was not flagged under current thresholds.

Monitoring & retrain triggers

The system is re-checked, not left running indefinitely: score drift across months, a shift in the action-mix distribution above, or a sustained drop in a periodic top-20 manual precision spot-check all signal it is time to retrain — ideally against a real future-window label once one is available, not on a fixed calendar.
